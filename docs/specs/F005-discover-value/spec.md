# F005 · 阶段 1：发现高价值问题规格

## 目标与可观察结果

FDE 从继承简报、客户资料、真实流程知情者和代表案例出发，分开保存“卖出的说法、人员陈述、现场观察、系统行为和政策授权”，判断哪个工作流问题值得继续，并明确安全回退、证据缺口和下一项现场动作。

## 来源与范围

- 来源需求：REQ-003, REQ-006, REQ-007, REQ-018, REQ-019, REQ-025, REQ-026, REQ-028, NFR-002, NFR-004, NFR-011, NFR-013, NFR-014
- 来源总规格：PSC-003, PSC-005, PSC-006, PSC-015, PSC-021, PSC-022, PSC-023, PSC-024
- 本 Feature 包含：阶段 1 工作台、现场资料与观察、方法路由、必要 Artifact、冲突重构和 FDE 决定。
- 本 Feature 不包含：完整价值经济性、技术方案选择、代码实现和生产批准。

## 阶段能力与 Skills

| 层级 | 能力 | 使用条件 | 预期结果 |
|---|---|---|---|
| 方法核心 | `qualify-ai-workflow` | 所有候选工作流 | 发现结论、工作流边界与 Workflow Charter starter |
| 方法条件 | `reframe-ai-engagement` | 关键现场事实推翻继承简报或角色说法冲突 | 可追溯冲突、安全回退和有权处置 |
| 工程核心 | `fde-orient`、`knowledge-interview`、`ownership-map` | 建立项目、访谈和责任线索 | 项目章程、访谈证据和角色图 |
| 工程条件 | `repo-recon`、`stakeholder-brief` | 问题明确涉及既有系统；需要管理者评审 | 初步系统线索或决策简报 |

Skill 只形成候选 Artifact 和方法 disposition，不替代客户事实或阶段决定。

阶段 1 不再注册一个包办全部工作的复合 Skill。真实路由顺序固定为：

1. 默认由方法 Skill `qualify-ai-workflow` 判断真实工作流是否值得继续；只有现场事实推翻继承边界、成功标准或停止条件时，才追加 `reframe-ai-engagement`。
2. 工程 Skill 按缺口加载：项目首次定向使用 `fde-orient`，需要向真实知情者取证时使用 `knowledge-interview`，需要确认维护者或决策人时使用 `ownership-map`，问题明确落到既有代码时使用 `repo-recon`，需要向管理者提交决定时使用 `stakeholder-brief`。
3. 任一请求只加载当前方法和必要工程 Skill，不得把上述 Skill 全部加载来制造“完成感”。

### 首轮项目内页面合同

从项目中心点击“进入项目”后，默认打开当前项目的阶段工作台，而不是空白会话首页。第一阶段页面围绕一句业务目标组织：

> 先弄清客户现在怎么做、哪里出了问题，再决定先解决什么。

目标下方用一句补充说明范围：“结合客户资料、访谈和实际案例，还原实际流程，确认问题影响、责任人和结果判断方式。事实没弄清前，不急着定方案。”

页面按以下职责分工：

1. 左侧项目上下文只展示项目身份、八阶段位置和返回项目中心入口，不再重复提供 Agent、上传或全局项目与会话树入口。
2. 主工作区展示第一阶段的四步引导、当前建议和待确认业务流程；待确认业务流程是从客户模糊诉求中逐步识别出的真实业务流程候选，文件只是承载事实和结论的载体。
3. DeepSeek Harness 原生输入框是唯一的 AI FDE 执行入口。用户可以直接描述客户诉求，也可以通过输入框内的轻量附件动作上传客户资料；页面不再创建第二个文本框、发送按钮或“Agent 执行入口”说明条。
4. 右侧阶段记录首次进入时默认收起为贯穿工作区高度的窄侧轨。收起态只显示记录图标与三项必备记录完成数；鼠标悬浮或键盘聚焦图标时，以单行浮层说明“本阶段记录”和当前数量，不在窄栏内竖排、折行或截断业务文字。展开后先展示本阶段已归档的客户原始资料，再展示“客户现状记录、待确认事项、业务流程说明”和按需出现的“项目调整记录”，明确区分阶段输入与阶段输出。客户原始资料点击后复用当前项目右侧文件预览；不支持在线渲染的格式仍保留归档和下载能力，不另建第二套预览弹窗。记录存在只表示形成初稿，不表示客户已经确认。
5. Agent 输入框中的“有客户资料？上传”是带文字的常驻操作，不再重复显示同文案悬浮提示；文件选择结束后页面不得残留遮挡输入框的上传提示。侧边栏等仅显示图标的上传入口继续使用悬浮说明。
6. 原生输入框归属左侧执行列，并停靠在“当前工作、候选工作流”之后；它不得横跨或遮挡右侧产物列。桌面工作台固定在当前可用视口内，页面本身不因工作区内容产生额外纵向滚动；左侧业务内容和展开后的产物区在各自区域内滚动。左侧执行列必须直接使用 Harness 发布的输入框实时高度预留空间，不得依赖固定像素猜测输入框高度。阶段工作台不常驻单独的 FDE 阶段门卡片：未就绪时由右侧产物逐项说明缺口；材料达到可评审状态后，才在产物区出现紧凑的“提交 FDE 评审”动作。
7. 项目文件树、代码、Diff、终端和浏览器作为按需技术工作区。进入阶段时不默认展开；用户从阶段推荐动作进入 Agent 对话时，左侧阶段导航自动收起，右侧当前项目文件树自动展开。点击预览产物或进入其他技术任务时，也只能在当前项目边界内展开。
8. 当前阶段项本身作为默认收起的工作方法目录开关，不再显示“本阶段工作方法”二级入口。目录只展示本阶段实际内置方法的业务名称和分组数量，不显示技术 Skill 名称，也不扫描电脑、全局配置或其他项目中的 Skills。点击阶段项展开目录后，用户可逐项查看方法用途；交付路径区域独立纵向滚动，确保下方阶段仍然可达。点击方法从右侧打开只读详情，使用 Markdown 渲染该内置 Skill 的完整定义，并把原始 Skill 名称和固定来源收纳在默认收起的“技术信息”中。该目录只用于解释平台会怎样协助当前阶段，不提供运行、安装、启用或编辑动作；实际执行仍由 DeepSeek Harness 原生输入框和按事实缺口自动路由承担。

对话承担自然语言沟通、Skill 路由、工具调用和过程留痕，但不承担解释整个阶段或替代 FDE 决定。用户无需知道 Skill 名称。

### 页面信息架构与交互优先级

阶段 1 页面必须按“理解目标、跟随四步引导、识别候选工作流、复核阶段产物、由 FDE 决定”的顺序组织：

1. **阶段定位不重复**：左侧阶段导航负责回答“当前在哪里”；主页面只用一句直接的业务目标说明“这一阶段为什么存在”，不得再次展示项目名称、阶段编号或完整八阶段流程。
2. **四步引导常驻**：始终显示“听客户怎么说、还原实际流程、确认是否值得做、决定下一步”四步。它们使用一条连续进度轨道，只突出当前步骤并标注“正在进行”，仅对紧邻下一步标注“下一步”，已完成步骤标记“已完成”，其余后续步骤保持弱化，不重复显示“等待前置事实”。轨道上方仅显示“本阶段进度 第 N/4 步”，不再用四个箭头卡片或重复的顶部进度线。
3. **原生输入框是唯一入口**：用户从 DeepSeek Harness 原生输入框开始，以自然语言描述诉求或继续多轮澄清。输入框内提供“有客户资料？上传”的轻量动作；上传只归档，不自动触发 Agent，也不代表模型已读取。
4. **当前引导不制造第二入口**：主区只说明当前要做什么、为什么做和建议怎样表达。第一步以“从一个最近发生的案例开始”为主任务，唯一主动作是“开始梳理真实流程”；项目已有资料时才补充“根据客户资料开始梳理”，只有系统已经记录重大说法冲突时才显示“继续核对说法不一致”。这些动作把有边界的任务交给原生对话，不等于第一阶段只有这些 Skill；平台仍按事实缺口路由已固定的方法与工程 Skill。不得再出现独立 Agent 卡片、资料大卡或第二个输入框。
5. **待确认业务流程逐步显现**：对话中识别出的真实业务流程必须持久化后作为主区的阶段性结果展示，包括参与角色、触发条件、真实问题、当前 disposition，以及已确认／推断／未验证证据数。该区域不是第二个操作入口，也不是系统内部工作流展示：无内容时只保留一条紧凑引导，不得用大面积空状态占据执行空间；有内容时使用可扫描的单列紧凑列表，默认展示业务流程名称、现状摘要和核对状态，详细事实按需查看。
6. **Artifact 与缺口合并展示**：右侧把底层“现场观察记录、事实确认清单、工作流章程、项目重新界定记录”分别呈现为“客户现状记录、待确认事项、业务流程说明、项目调整记录”。前三项是必备记录，第四项仅在重大冲突时需要。每项用真实业务语言说明用途和当前状态，已有载体可点击预览；不再另设内容重复的“证据与缺口”面板，也不向用户暴露 `DOC`、`IF`、结构等级等内部术语。
7. **FDE 评审留在当前项目**：候选 Artifact 未齐时，产物项直接展示缺口；候选材料齐全后，右侧才出现“提交 FDE 评审”。点击后在当前项目内进入第一阶段评审模式，不返回项目中心、不新建会话，也不改变阶段。评审页集中核对当前选择的业务流程、客户原始资料、逐条证据、三项必备记录、按需记录和未确认事实。FDE 可选择“进入下一阶段、继续补充调查、缩小问题范围、暂停这个问题”；只有“进入下一阶段”经过二次确认后调用持久化阶段服务，其余决定均留在第一阶段并把可编辑任务交给原生 Agent 对话。
8. **执行入口与产物互不遮挡**：桌面端原生输入框只占左侧执行列，右侧产物在任何输入框高度下都保持可读、可预览。页面读取 Harness 实时发布的输入框高度，并直接从左侧执行列的可用高度中扣除输入框占位；不得仅在滚动内容末尾追加空白来假装预留，不得使用固定高度，也不得通过整页大面积底部留白解决遮挡。阶段状态刷新并切换当前工作时，左侧执行列必须回到顶部，让阶段目标和新工作完整出现；右侧材料齐备后的评审说明与按钮必须在产物列内纵向排列并完整可达，不得被列宽、容器底部或输入框裁切。
9. **工作方法目录不制造技术门槛**：阶段项直接展开的目录必须回答“平台能帮我做什么”，第一阶段依次展示“项目启动与方向确认、访谈业务人员，还原真实做法、找到负责人和决策人、盘点现有系统与资料、判断问题是否值得继续投入、核对冲突并调整项目范围、整理给负责人看的决策简报”。目录默认收起，阶段项展开和详情切换采用轻量即时反馈；详情关闭后保持原阶段工作台位置和输入状态。目录中的完整 Markdown 必须来自 Host 已注册的固定版本 Skill，前端不得复制或重新解释为另一套方法定义。

桌面端按浏览器 100% 缩放设计可读性：业务正文与操作文字不得使用微型说明字号，关键说明至少采用正常正文层级；只有编号、状态缩写和非关键元数据可以使用紧凑字号。弱化信息通过颜色和层级区分，不能仅靠缩小字体隐藏。

### 前后端阶段投影合同

Host 对第一阶段输出稳定的业务投影，页面不在渲染时临时猜测阶段结论：

- `status`：`collecting`、`understanding`、`qualifying` 或 `ready-for-review`；
- `currentWorkId`：当前主工作，由真实候选 Artifact 状态确定；
- `route`：投影当前阶段已固定版本的方法 Skill、工程 Skill、来源 commit 和条件，不把 Skill 名称作为用户操作门槛；
- `artifacts`：底层仍以“现场观察记录、事实确认清单、工作流章程”和条件性的“项目重新界定记录”作为稳定 Artifact 合同，同时读取 `.fde/discovery/artifacts.json` 中的来源适配器、内容版本、结构成熟度和逐条证据引用；前端只做业务名称映射，不修改文件路径与后续 Skill 输入合同；
- `workflows`：读取项目内 `.fde/discovery/workflows.json` schemaVersion 2，投影已持久化的候选工作流、当前选择和逐条 `evidenceRefs`；页面显示的已确认／推断／未验证数量只能从这些引用聚合，不能由 Agent 单独填写计数；
- `reviewReady` 与 `blockers`：只有三项必备文件存在、Artifact Catalog 有匹配记录、结构至少达到 `starter_valid`、来源版本合法且至少有一条逐条证据引用时才可评审；它仍不代表客户确认或阶段自动完成。

客户原始资料仍由项目 Source API 独立加载，并与阶段投影在前端组合；任一读取失败都显示本区域错误，不降级为空数组或 0。

页面的首要操作必须是当前推荐工作，项目文件树、执行轨迹和通用对话属于支持面。频繁操作采用轻量、即时反馈；不得用大面积装饰、同权重卡片或技术黑话稀释当前任务。

## 功能行为

### 主流程

1. 保存原始资料而不把上传解释为 Agent 已读或事实成立。
2. 引导用户找到真实流程知情者、一个正常案例和一个重要异常案例。
3. 用户点击推荐动作时，系统切换到原生 Agent 对话，收起左侧阶段导航、展开右侧当前项目文件树，并把一段可编辑的业务问题预填到原生输入框；用户补充或确认后手动发送，页面不得代替用户立即发起对话。
4. 用户发送业务问题后，平台通过当前阶段的后台提示路由 `qualify-ai-workflow`，只加载当前任务所需参考与工具；Skill 名称、逐条证据格式、上下文限制和阶段控制规则不得出现在用户消息中。
5. 当关键说法冲突并改变边界时，条件触发 `reframe-ai-engagement`。
6. 形成 Field Observation Log、Workflow Charter starter，并在需要时形成 Engagement Reframe starter。
7. 工作台展示当前引导、候选工作流、Artifact 及其事实缺口；材料齐备后可进入当前项目的第一阶段评审模式。
8. FDE 在评审模式核对当前业务流程、资料来源、证据状态、必备记录和未确认事实；进入评审模式本身不得修改阶段。
9. FDE 选择“进入下一阶段”后必须再次确认，并携带当前阶段修订号调用既有持久化阶段服务；成功后直接呈现第二阶段。继续调查、缩小范围或暂停只预填可编辑的 Agent 任务，不得推进阶段。

### 结构化持久化合同

`.fde/discovery/workflows.json` 固定使用 `schemaVersion: 2`。每个候选工作流必须包含 `evidenceRefs`，每条引用至少包含稳定 `id`、`state`、`kind`、`ref` 和 `summary`。`state` 只能是 `confirmed`、`inferred` 或 `unverified`；`kind` 只能表示项目文件、对话、访谈、观察、系统、政策或外部来源。数量只由 Host 对引用聚合得出。

`.fde/discovery/artifacts.json` 固定使用 `schemaVersion: 1`。每个 Artifact 记录固定 `id`、正整数 `version`、`contentPath`、`sourceAdapter`、`structureState`、`evidenceState`、`evidenceRefs`、`inputRefs`、`decisionRefs` 和 `supersedes`。其中：

- 三项必备产物的规范 ID 依次为 `research-report`、`confirmation-checklist`、`requirement-baseline`，条件产物为 `engagement-reframe`。兼容已经由早期提示生成的 `requirement-research-report`，Host 读取时必须规范化为 `research-report`；新写入不得继续使用别名。
- Artifact 的 `evidenceRefs` 规范写法与候选工作流一致，保存完整逐条证据对象。兼容已经生成的证据 ID 数组，但每个 ID 必须能在当前 `workflows.json` 的逐条证据中解析；Host 使用原始证据状态、类型、来源和摘要完成投影，未知 ID 继续明确阻断，不能凭 ID 伪造证据。
- `inputRefs`、`decisionRefs` 和 `supersedes` 使用字符串数组；历史记录中的 `supersedes: null` 等价于尚无被替代版本，新写入统一使用空数组。
- `sourceAdapter` 必须记录来源仓库、已审查 commit、许可证和上游 Artifact 名称；工作台本地合同使用自身固定适配器版本。
- `structureState` 只能是 `missing`、`invalid`、`starter_valid`、`complete_valid` 或 `not_applicable`。Host 还必须核对实际 Markdown 的最小章节，不能只接受 Agent 自报状态。
- `evidenceState` 与逐条引用分离保存；Agent 不能因为结构有效就把证据标为已确认。
- 文件存在但没有合法 Catalog 记录、来源版本不匹配、缺少最小章节或没有证据引用时，页面必须显示“结构未登记／结构无效”，阶段门不得放行。

项目阶段工作台每次进入时必须从 Host 重新读取当前项目快照和资料列表，不能复用进入 Agent 对话前的缓存。若工作台保持打开，Agent 从运行转为完成时必须再次刷新；刷新结果同时更新四步阶段进度、三项必备记录状态和候选业务流程。读取失败必须显示具体错误，不得继续展示旧的 0 项或 0/3。

### 业务规则与边界

- 没有流程知情者、代表案例、结果验证者、可访问上下文或风险上限时，不能进入方案设计。
- 基线未知必须写为未测，不能由 Agent 估算成现场事实。
- `discover`、`defer`、`do_not_build` 是方法结论；项目阶段仍由 FDE 记录 Go／Revise／Narrow／Stop。

## 异常与恢复

| 情况 | 用户可见状态 | 系统行为 | 恢复/重试 |
|---|---|---|---|
| 只有演示资料，没有代表案例 | 缺少现场证据 | 保持 Artifact 待验证 | 添加近期案例后重跑 |
| 冲突缺少有权处置人 | 等待责任人 | 保存冲突和安全回退，不默认同意 | 补充权限依据和处置 |
| Skill 或 Artifact 校验失败 | 工作失败或结构无效 | 保留输入和执行轨迹，不发布有效 Artifact | 修复字段或适配器后重试 |
