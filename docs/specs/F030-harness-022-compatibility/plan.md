## 实现方案

### 三方合并与空间

在唯一主工作树中进行；用 Git 对象将旧、新官方根树映射到 `upstream/deepseek-harness/`，通过显式 merge-base 的 `git merge-tree` 计算，机械应用无冲突内容，冲突逐项保留 FDE 语义并适配新版。旧源码由本地提交恢复，不另存完整源码/依赖树。合并树 ID、冲突清单与日志放在被忽略的 `.runtime/harness-022-upgrade/`，验收及回退窗口结束后可清理。

起始磁盘空余约 7.3 GiB。复用现有 node_modules 与下载缓存；预估运行区和项目非秘密副本约 22 MiB，不复制浏览器缓存、node_modules、构建目录或凭据。每轮大体积安装前检查剩余空间，不能为升级删除其他项目。

### 适配重点

1. 官方 Node 下限提升为 24.9，当前 Node 24.16 满足；pnpm 仍锁定 11.28.5。安装时根据三方合并保留本地 OpenAPI、FDE 包、固定 Eval 和必要第三方补丁，不滚动升级无关包。
2. 对照官方指南适配 SessionStore 创建/宣告后写入、投影注册句柄、Agent ownerAgent 与 Session.append 两种重载，重点覆盖业务访谈、阶段和用量读取。Session v4 原件仍不可覆盖。
3. 工具执行器从 Tools 配置拆出，复用目标 base 的正式组合；自定义训练测试组合补齐执行器，不能以假工具结果替代资料授权。终端保持 FDE 已确认的只读运行输出与独立手动命令，不因新版可选终端自动授予用户终端读取。
4. 保留 Native/Web 页面 Peer 授权与所有 FDE owner-only 路由。官方可选插件容错不能掩盖 FDE 必需入口未加载。
5. 自定义浮层、桌面导航检查新版显式窗口拖动区域；保留 Logo 48 px 安全区、非全屏范围与中文挑战原生 fetch 普通函数调用。
6. 官方新增默认搜索计费、归档清理工作树、团队协作、Office 执行等能力按原配置边界审阅；本轮不自动开启付费、外发、删除或额外目录访问。接口必须变更时先记录技术影响，行为需要扩展则停下请求用户确认。

### 已落实的兼容裁决

- 保留 FDE 的 WorkspaceBrowser、项目创建信息表单和旧行菜单入口；共享 Controller、搜索、授权与新版上下文菜单 API 采用新版本，不用通用 Workspace 界面替换项目旅程。
- 会话视图导航保留按 Session 的独立 action 映射，避免与新版页头 actions 可观察状态重名；会话内容和品牌插槽同时保留 FDE 与新版扩展点。
- 业务实验室每个角色作用域显式挂载原生工具执行器，保留工具白名单、守卫及独立 Session。投影注册改为等待句柄，既有活动投影的状态格式不变。
- `dsh-better-sidebar` 固定 0.31.1，`dsh-observe` 固定 0.2.27；File Review 0.5.0 沿用并验证 Typert、工具消息和列表插槽补丁，兼容声明精确限定 0.2.2-rc.2，不使用全局版本豁免。本地 OpenAPI 和固定 Eval 仍保留。
- 关闭 Session 自动上传的配置落在真正的 `session-log-deepseek` 行，不使用新版已不存在的 `$main` 层。遥测与观测导出仍关闭；Forge/工作树清理不属于默认启用组合。
- Skills 阅读器的 `fileLinks` 仅打开集合内已知文件，未知文件和应用协议不回落到更宽泛的系统文件委托。普通对话的官方 Markdown 行为不受该可选 prop 约束。

### 数据与交付细节

当前实际数据事实源是 `.runtime/harness-021-validation/dsh-home` 与同级 `workspaces`，不是更早的 `.runtime/dsh-home`。只创建一次 `.runtime/harness-022-validation/`，复制项目、登记、阶段、Session、业务访谈 SQLite 和挑战状态；排除凭据、环境文件、令牌、profiles 依赖和 Electron 用户目录。SQLite 在旧 Host 已停止后复制；记录源/副本 hash，项目复制保留精确 mtime。工作区目录、Session 首帧 cwd 和目录键仅在副本中改写，后续事件 frame 不重压。原运行区继续留存。

先无密钥启动 Web 3083 验证实际 Boot、认证、Workspace 和新旧记录，最后以该隔离 home 启动桌面端交用户体验，不让两个 Host 并发写同一份状态。没有模型密钥时保持无密钥能力可用，不读取受保护凭据库或复制旧凭据补齐配置。

## 实施顺序

1. 当前代码检查点、F030 文档和风险记录。
2. 停止旧 Host；保存必要数据副本及摘要。
3. 三方合并并解决直接冲突。
4. 安装、构建，依据真实错误做最小 API 与第三方适配。
5. 执行直接相关无密钥检查与一次历史恢复验证。
6. 核对在线资源、启动桌面，记录未验证项与人工验收入口。

## 回退策略

停止新版后，只撤回 F030 的明确源码差异并重建锁定依赖，使用本地检查点 `53bb3e0dc8` 对应源码和一直保留的旧 `.runtime/harness-021-validation`。不 reset --hard，不删除用户修改，不用旧代码打开新版已写数据；测试副本和合并日志在人工验收及回退窗口结束后可清理。
