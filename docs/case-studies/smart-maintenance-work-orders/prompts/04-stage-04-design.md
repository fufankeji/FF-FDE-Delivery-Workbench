# 阶段 4 提示词：设计方案并完成端到端纵向切片

## 前置条件

- 阶段 3 已由 FDE 人工决定进入阶段 4。
- 继续使用前三阶段的同一个项目和原 SourceId，不重复上传已有材料。
- 按 `STAGE-04-RUNBOOK.md` 操作；`STAGE-04-EXPECTED-EVIDENCE.md` 只供操作者核对，绝对不要上传。
- 本阶段可以使用 Semantica 构建代表性最小图谱，但不进行全量建图、生产写入或阶段推进。

## Prompt A：进行双轴机制判断

```text
当前进入阶段 4。请固定读取阶段 2 的结果合同、阶段 3 的数据／系统／治理产物和本次方案约束，先做双轴机制判断，不要直接开始建图或写代码。

第一轴回答“系统如何执行”：比较不构建／人工改进、确定性规则、传统软件、检索／RAG、ML／LLM、有界 Agent 和多 Agent，允许组合，但要给出主机制、辅助机制、不采用项、确定性回退和退出条件。

第二轴回答“系统如何表达和查询领域事实”：比较普通数据／接口 Schema 与正式本体／知识图谱。必须依据跨来源身份统一、关系复杂度、多跳查询、时间有效性、来源追溯、冲突处理和共享上下文的真实需要判断；不能因为已经安装 Semantica、资料很多或想展示图谱就选择正式本体。

把两轴的适配性、风险、成本、缺失证据、权限边界和当前候选写入 mechanism-selection.md。明确本体必要性是“需要”“不需要”还是“证据不足”，并更新 design.json 的 mechanism 工作项；不要把“需要”写成已经验证通过，也不要推进阶段。
```

预期内部路由仅供学习对照：机制选择；只有第二轴有充分证据时才进入条件本体／知识图谱能力。

## Prompt B：定义能力问题和最小 Ontology

```text
本次双轴判断如果已经有证据选择正式本体／知识图谱，请读取语义能力问题工作坊，并只绑定当前项目中获准且版本固定的代表材料；不要要求我重复上传，也不要读取未绑定资料。

1. 将业务问题整理成可真实查询的能力问题，保留重复候选、跨系统事件链、合同时间有效性、来源变化影响、安全权限和 Agent 最小上下文六类问题。
2. 从材料生成候选 Ontology Schema，明确类、属性、关系方向、Domain／Range、必填／唯一／基数约束、别名、身份匹配键、来源、有效时间、置信度和冲突规则。
3. 严格区分 Schema 与实例；抽取结果先进入候选集合，低置信度、来源冲突和高风险关系不得自动成为正式事实。
4. 把 `final_domain`、`final_priority` 等历史答案隔离在候选生成上下文之外。
5. 将候选 Schema、来源规则、时间规则和待处理冲突呈现给我审阅；在我人工确认前保持草稿，不发布当前 Ontology 版本，不开始构建图谱。

同时把路线、组件、接口、权限、人工门禁、失败恢复、NFR 和条件本体设计更新到 solution-design.md，并更新 design.json 的 architecture 工作项。只使用系统登记的条件本体对象，不自行创建平行最终稿。
```

预期内部路由仅供学习对照：生产级系统设计＋方案设计＋合同设计＋NFR 基线＋条件本体设计。

## Prompt C：构建并独立验证最小知识图谱

```text
我已经人工审阅并发布当前 Ontology 版本后，请使用项目级 Semantica Provider 和已绑定的代表材料执行最小图谱与业务循环；若没有已发布版本或 Provider 不可用，立即停止并如实记录，不得用说明文字或演示图替代运行。

1. 固定 Workspace、材料版本、Ontology 版本、来源／时间／置信度规则、Provider 版本和配置。
2. 分步执行解析、抽取、身份匹配、去重和冲突处理；候选、拒绝项和正式图谱分别留痕。
3. 在当前项目隔离图中构建实例，保存真实节点／关系摘要和诊断。不得复用其他项目或全局演示图。
4. 独立运行结构校验；随后在当前项目图谱上真实执行全部必答能力问题，保存每次查询、结果、来源、有效时间、置信度和未解决项。
5. 构建成功、结构校验和能力问题通过分别记录；任何一步失败都不能把本体路线写成 validated。

不要调用生产接口，不创建 Sandbox 或正式工单，不推进阶段。
```

## Prompt D：用受控图谱上下文跑通业务切片

```text
请基于当前已验证的图谱版本，为南京新街口店 R-1002／R-1003 获取一次项目级受控上下文，并真实执行“报修输入 → 重复候选 → P0 硬门 → 设备／告警／合同／维修商查询 → 有引用建议 → 本地工单草稿”的最窄纵向切片。

上下文只能返回本任务必要的实体、关系、规则、来源、有效时间、置信度、权限和未知项；禁止注入整张图谱、其他区域数据或 final_* 历史答案。P0 提示必须走确定性路径且不能等待模型；设备身份、告警或合同存在不确定时必须转人工。维修商只能是候选，不得表达成已批准。

当前没有 Sandbox 草稿写权限，因此动作终点只能是本地草稿。保存真实输入、图谱查询、返回子图或答案、Agent 使用方式、业务结果、失败点、外部写入未执行声明和回滚方式到 vertical-slice-record.md，并更新 design.json 的 slice 工作项。没有真实运行证据就保持未完成。
```

## Prompt E：整理阶段评审

```text
请重读 mechanism-selection.md、solution-design.md 和 vertical-slice-record.md，确认它们引用同一批阶段 2／3 输入、当前 Ontology、图谱、规则、Provider 和上下文版本。

分别列出：双轴机制结论、Schema 与实例边界、构建运行、独立结构校验、六个能力问题真实查询、受控 Agent 上下文、业务纵向切片、权限边界、失败和待重评项。只有当前版本的结构校验、必答问题查询和上下文业务切片都形成可引用证据时，本体机制结论才可候选为 validated；否则使用 validation_failed 或 insufficient_evidence。构建成功、文件存在或图谱可浏览不能替代验证。

更新 design.json 的 mechanism、architecture、slice、decision 四个工作项和 review-ready 条件，最后输出给 FDE 的评审摘要。本体机制结论与 FDE 的 Go／Revise／Narrow／Stop 决定必须分开；不要替我提交决定或进入阶段 5。
```

## 人工检查

- 是否选择了混合机制，而不是把全部工作交给模型。
- 是否先进行了“执行机制 × 语义基础”双轴判断，而不是默认建图。
- 是否分开保存 Ontology Schema、实例图谱、构建、校验、能力问题和上下文运行。
- 是否把 P0、权限、幂等和读回放在受信任边界。
- 是否包含正常、拒绝、超时、冲突和恢复路径。
- 是否清楚区分“需要本体”“构建成功”“验证通过”“切片通过”“FDE 决定”和“生产就绪”。
