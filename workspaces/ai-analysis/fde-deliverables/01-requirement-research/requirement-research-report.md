## 1. 业务背景与目标

### 1.1 背景（事实）
星桥生活电商经营四个主要销售渠道（自营商城、天猫、京东、抖音），在华东、华南、华北设三个仓配节点（佛山仓、昆山仓、廊坊仓）。经营分析团队每天上午从 OMS/WMS/CRM/售后/商品/目标等系统导出文件，在 Excel 中人工拼接后向管理层发日报。

### 1.2 核心痛点（事实）
公司**不是缺报表**，而是缺少「从一个经营问题 → 到可信答案」的**连续、可追溯过程**：

| 现状 | 表现 | 业务影响 |
|---|---|---|
| 日报制作 | 约 23 个导出文件、2~3 小时/天 | 会议前只能给结果，无法解释变化原因 |
| 指标口径 | GMV/退款率/复购率至少 6 套版本 | 同一会议出现不同数字，反复对账 |
| 临时分析 | SQL/Python/图表散落个人目录 | 难复现、难交接，分析 0.5~2 工作日/次 |
| 模型实验 | 零散 Notebook，参数未登记 | 无法判断模型版本是否可用于新数据 |
| 报告输出 | 复制粘贴 PPT/Word | 来源与更新时间不清，修改成本高 |

### 1.3 目标（事实 / 推断）
- 建立**项目化分析空间**：每个经营问题有独立的数据源、查询、图表、模型、报告与分析记录。
- 统一接入 **CSV、Excel、SQLite 与 MySQL 只读** 数据源，保留字段画像、基线与来源指纹。
- 支持**自然语言提问**，同时能看到实际执行的 SQL、数据范围与生成产物。
- 支持质量检查、清洗、特征工程、分类/回归/聚类实验与模型横向比较。
- 保留数据片段、SQL、代码、图表、模型、预测与报告之间的**关系（血缘）**，便于复核和继续工作。
- 报告以 Markdown 为底稿，可生成管理层查看的正式版本；**无在线模型时确定性能力仍可用**。

### 1.4 期望业务结果（事实）
| 结果 | 当前基线 | 一期期望 | 说明 |
|---|---|---|---|
| 日常报表效率 | 2~3 小时/天 | ≤30 分钟初稿 | 保留人工确认、非全自动 |
| 临时问题响应 | 0.5~2 工作日 | 常见问题 ≤30 分钟可复核 | 复杂问题不以“秒级”为目标 |
| 分析可追溯 | 依赖个人文件 | 关键结论回到数据/SQL/图表/模型 | 至少项目级版本 |
| 模型使用 | 零散实验 | 一套可复现复购预测基线 | 验收指标待确认 |
| 报告交付 | 手工复制粘贴 | 周报由选定产物生成、持续编辑 | 图表标注来源与版本 |

### 2.2 首批高频分析场景（事实）
| 场景 | 典型问题 | 期望输出 |
|---|---|---|
| 经营概览 | 昨日 GMV/订单量/客单价/退款率为何变化？ | 趋势、渠道/区域拆解、异常说明、可复核查询 |
| 履约分析 | 华南仓延迟上升来自承运商、仓库还是商品结构？ | 按仓库/地区/品类/承运商分层的延迟率与明细 |
| 客户分群 | 新客、复购客、高价值客有哪些特征？ | 可保存的分群数据片段与画像说明 |
| 复购预测 | 哪些首购客户 30 天内更可能复购？ | 训练数据、特征、模型指标、预测、复现代码 |
| 售后归因 | 某活动期间退货率上升是否集中在少数 SKU？ | 异常 SKU、订单明细、活动对比、证据图表 |
| 经营报告 | 把本周确认结论整理成周报并保留版本 | 带数据来源、图表、结论的报告版本 |

## 3. 现状流程（事实）

以工作日每日经营日报为主线：

```
07:30 多系统导出  → OMS / WMS / CRM / 售后 / 目标表
08:30 人工拼接    → 关联订单、履约、商品与会员字段（按 order_id 关联）
09:30 口径核对    → 检查渠道映射、退款与承诺时效（套用人工维护的类目映射表）
10:30 报表发布    → 复制图表、补充说明、群内发送；一份日报约 17 个固定区域
```

**典型问题（事实）**
- 现有 Excel 通过“复制上日工作表”完成，部分公式引用本机绝对路径，他人打开失效。
- 临时问题（如延迟率上升）需在 WMS 导出明细后，再拼接承运商/仓库/地区/类目；下钻保留但**订单号可显示，收件人姓名/手机号/详细地址默认不得展示**。
- 指标口径、渠道枚举、历史类目映射等缺乏统一版本化管理。

## 4. 目标流程（推断）

```
业务问题(自然语言) → 说明将使用哪些数据 → 执行只读查询 → 保存数据片段
   → 质量画像/清洗/特征工程(生成新产物) → 图表(引用已存产物)
   → 模型实验(登记指标/代码/逐行预测) → 报告(引用产物, 版本化)
   → 任一环节可回溯返回, 结论可追溯到数据/SQL/图表/模型
```

关键特征[推断/事实]：资产只有“明确绑定”后才进入项目；查询默认只读；结果落为项目数据片段；所有处理生成新产物、**不覆盖原始数据**。

## 5. 系统与数据

### 5.1 数据源现状（事实）
| 数据源 | 类型 | 历史规模 | 日增量 | 更新时间 | 主要内容 | 当前问题 |
|---|---|---|---|---|---|---|
| OMS 订单库 | MySQL | 主表 186 万/明细 542 万 | 1~1.8 万单 | 每日 07:30 | 订单/支付/渠道/活动 | 退款回写滞后、渠道枚举不统一 |
| WMS 履约库 | MySQL | 约 179 万 | 约 1.5 万 | 每日 08:00 | 仓库/承运商/承诺/实际送达 | 节假日规则未结构化 |
| CRM 会员导出 | Excel | 约 42.3 万 | 每周约 0.4 万 | 每周一 | 等级/注册/首购/标签 | 含手机号地址，需脱敏 |
| 售后明细 | CSV | 约 8.2 万 | 300~600 | 每日 08:00 | 退换货/退款/原因 | 一单多售后、原因码不全 |
| 商品中心 | Excel | 约 3.6 万 SKU | 不定期 | 人工上传 | SKU/类目/品牌/成本参考 | 历史类目映射缺失 |
| 经营目标 | Excel | 每月约 200 行 | 每月 | 每月 1 日 | 渠道/活动/经营目标 | 群聊多版本、无统一版本号 |

### 5.2 现场确定的数据原则（事实）
- 生产库必须用**只读账号**，查询由 IT 提供的账号与网络范围控制。
- 原始文件/快照不得因清洗或特征工程被覆盖；新结果形成新产物。
- 字段画像需记录来源版本或指纹；来源变化后旧结果应提示可能过期。
- 客户姓名/手机号/地址/身份证号**不进入首期样例**；会员 ID 需**不可逆映射**。
- 第一阶段可用脱敏文件验证流程；是否直连 MySQL 作为验收前置**尚未确认**。

### 5.3 样例数据（05 CSV，520 行 / 27 列）（事实/推断）
字段覆盖：订单明细（order_id/order_line_id/商品/金额/状态）、履约（warehouse/carrier/promised/shipped/delivered）、客户（customer_level/first_order_flag）、渠道（channel/campaign_code）等。
- 刻意保留的数据问题（与需求一致）：**4 条重复明细**、字段缺失（`delivered_at` 67 空 / `aftersale_type` 497 空 / `satisfaction_score` 264 空）、**枚举不一致**（channel 同时有“抖音”与“抖音商城”）、**异常评分**（satisfaction_score 最大 6，越界）。
- 已验证可支撑“数据质量检查”验收项。

## 6. 范围

### 6.1 必须具备（事实）
- 本地创建/重命名/归档/导出分析项目；项目间数据与产物相互隔离。
- 导入 CSV/Excel/SQLite 文件并连接 MySQL；连接默认只读。
- 展示字段画像、类型、空值、唯一值、最小/最大值与来源变化提示。
- 明确选择数据源后执行只读查询，结果保存为项目数据片段。
- 基于数据片段做质量画像、清洗、特征工程、图表保存、模型实验。
- 登记模型配置、指标、代码、模型文件与逐行预测，可比较历史实验。
- 根据选定产物生成报告；报告修改与恢复均形成新版本。
- 关键数据/查询/代码/图表/模型/报告之间可追溯。

### 6.2 希望一期尽量包含（事实）
- 自然语言分析入口：把业务问题转为查询/图表/分析步骤。
- 沉淀可复用分析 Skills（数据质量审计、履约异常、客户分群、完整报告）。
- 局域网多人访问、统一登录、部门级权限。
- 从 MySQL 定时同步每日增量，工作日上午 8:30 前完成更新。

### 6.3 明确不包含（事实）
- 直接修改 OMS/WMS/CRM/MySQL 生产库任何数据。
- 自动向客户发送优惠券/短信/运营触达（系统只输出结果与建议名单）。
- 替代财务结算或形成有会计效力的经营口径。
- 面向全公司的复杂协作、审批流与移动端应用。

## 7. 约束

### 7.1 部署与运行（事实）
- 原始经营数据优先保存在公司电脑或局域网环境；**单机试点与 20 人访问目标存在冲突**。
- 首期单机试点（3 名分析师）由 IT 评估约需 8 周（数据脱敏、只读副本、权限评审、局域网部署）。
- 浏览器：Chrome/Edge 当前稳定版；Windows 用户可 WSL2；是否原生运行 Windows 待确认。

### 7.2 安全与隐私（事实）
- 手机号/地址/姓名/会员标识**不得发送到外部模型**；需确认脱敏策略、模型部署方式与允许发送字段。
- 数据库账号/模型密钥/凭证不写入源码或导出包。
- 若使用外部模型，默认只发送字段名、脱敏样本与聚合结果；会员标识/订单号/原始明细是否可发需单独评审。
- 项目导出必须排除数据库密码、模型 API Key、日志中的敏感值。

### 7.3 性能（事实）
- 需求初稿：100 万行常见聚合查询 P95 < 10 秒（测试设备暂定 16 GB 内存 MacBook）。最大明细表超 500 万行。
- IT 需先定义测试设备/数据格式/查询集/是否允许预聚合；PPT“秒级回答”**不是所有问题的统一验收标准**。

### 7.4 可用性与恢复（事实）
- 无在线模型/模型凭证时，文件导入、只读查询、数据处理、建模与报告仍应运行。
- 服务异常重启不丢失项目、数据源设置、报告与模型产物。
- 脚本型分析能力需在**无网络沙箱**中运行并限制目录访问。
- 首期不建企业级审批流，但保留关键查询与模型实验的来源与时间。
