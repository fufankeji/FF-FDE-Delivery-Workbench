# 1. 项目背景与发起原因

星桥生活电商目前经营自营商城、天猫、京东、抖音四个主要销售渠道，在华东、华南和华北设有三个仓配节点。过去两年订单规模增长较快，数据仍主要依赖各业务系统导出后在 Excel 中拼接。经营分析团队每天上午需要下载订单、发货、售后、会员和活动数据，手工处理后再向管理层发送日报。

现有方式可以完成固定报表，但当业务提出“某渠道退货率为什么升高”“哪些新客可能在 30 天内复购”“华南仓延迟是否集中在特定品类”等问题时，分析师通常需要重新取数、核对字段、编写 SQL 并单独制作图表。一次临时分析从半天到两天不等，分析过程和代码散落在个人电脑，后续很难复用。

公司计划在 2026 年双十一前完成一期试点，希望先为经营分析人员提供一个本地优先的分析工作台，把数据接入、只读查询、质量检查、可视化、建模实验和报告版本放在同一个项目中。管理层同时提出未来应覆盖运营、供应链和用户增长岗位，但首期实际使用人数尚未最终确认。

## 1.1 当前工作量与主要问题

| **现状** | **当前表现** | **业务影响** |
| --- | --- | --- |
| 日报制作 | 每日约 23 个导出文件，2～3 小时人工整理 | 上午会议前经常只能给出结果，无法解释变化原因 |
| 指标口径 | GMV、退款率、复购率至少存在 6 套常用版本 | 同一会议中出现不同数字，业务需要反复对账 |
| 临时分析 | SQL、Python 和图表保存在个人目录 | 难以复现，人员休假时无法继续 |
| 模型实验 | 偶尔在 Notebook 中完成，训练数据和参数未统一登记 | 业务无法判断模型版本是否可用于新数据 |
| 报告输出 | 周报、月报主要复制粘贴到 PPT 或 Word | 图表来源和更新时间不清楚，修改成本高 |

# 2. 项目目标

- 建立项目化分析空间：每个经营问题拥有独立数据源、查询、图表、模型、报告和分析记录。
- 统一接入 CSV、Excel、SQLite 与 MySQL 只读数据源，保留数据画像、字段基线和来源指纹。
- 允许分析师使用自然语言提出问题，同时能够看到实际执行的 SQL、数据范围和生成产物。
- 支持数据质量检查、标准清洗、特征工程、分类/回归/聚类实验以及模型横向比较。
- 把数据片段、SQL、代码、图表、模型、预测和报告之间的关系保留下来，便于复核和继续工作。
- 支持 Markdown 作为报告内容底稿，并能够生成可供管理层查看的正式报告版本。
- 在没有在线模型时，数据接入、查询、建模和报告等确定性能力仍可运行。

## 2.1 期望业务结果

| **结果方向** | **当前基线** | **一期期望** | **说明** |
| --- | --- | --- | --- |
| 日常报表效率 | 2～3 小时/天 | 30 分钟内完成初稿 | 不要求完全无人值守，需保留人工确认 |
| 临时问题响应 | 0.5～2 个工作日 | 常见问题 30 分钟内形成可复核结果 | 复杂分析不以“秒级回答”为目标 |
| 分析可追溯 | 依赖个人文件 | 关键结论可回到数据、SQL、图表或模型产物 | 至少保留项目级版本 |
| 模型使用 | 零散实验 | 形成一套可复现的复购预测基线 | 验收指标仍需确认 |
| 报告交付 | 手工复制粘贴 | 周报可从选定产物生成并持续编辑 | 图表需标注来源和版本 |

# 4. 一期范围设想

## 4.1 必须具备

- 本地创建、重命名、归档和导出分析项目；不同项目的数据和产物相互隔离。
- 导入 CSV、Excel、SQLite 文件并连接 MySQL；连接数据库时默认只读。
- 展示数据画像、字段类型、空值、唯一值、最小/最大值和来源变化提示。
- 在明确选择数据源后执行只读查询，并把查询结果保存为项目数据片段。
- 基于数据片段完成质量画像、清洗、特征工程、图表保存和模型实验。
- 登记模型配置、指标、代码、模型文件和逐行预测；可以比较历史实验。
- 根据选定产物生成报告，报告修改与恢复均形成新版本。
- 关键数据、查询、代码、图表、模型和报告之间能够追溯。

## 4.2 希望一期尽量包含

- 自然语言分析入口，可以将业务问题转化为查询、图表或分析步骤。
- 沉淀可复用的分析 Skills，例如数据质量审计、履约异常分析、客户分群和完整报告。
- 局域网内多人访问、企业统一登录和部门级权限控制。
- 从 MySQL 定时同步每日增量数据，工作日上午 8:30 前完成更新。

## 4.3 本期明确不包含

- 直接修改 OMS、WMS、CRM 或 MySQL 生产库中的任何数据。
- 自动向客户发送优惠券、短信或运营触达；系统只输出分析结果和建议名单。
- 替代财务结算或形成具有会计效力的经营口径。
- 面向全公司的复杂团队协作、审批流和移动端应用。

# 5. 数据来源与现状

| **数据源** | **主要内容** | **历史规模** | **更新方式** | **当前问题** |
| --- | --- | --- | --- | --- |
| OMS 订单库 | 订单主表、订单明细、支付、渠道、活动 | 主表约 186 万行；明细约 542 万行 | MySQL，每日增量 | 退款状态回写滞后；渠道名称不统一 |
| WMS 履约库 | 仓库、出库、承运商、承诺/实际送达 | 约 179 万行 | MySQL，每日增量 | 节假日承诺日期规则未结构化 |
| CRM 会员导出 | 会员等级、注册渠道、首购时间、标签 | 约 42.3 万行 | Excel，每周 | 手机号和地址属于敏感信息，标签存在人工维护 |
| 售后系统 | 退货、退款、换货、原因和处理时间 | 约 8.2 万行 | CSV，每日 | 一笔订单可能有多条售后记录 |
| 商品中心 | SKU、类目、品牌、上下架和成本参考 | 约 3.6 万 SKU | Excel，不定期 | 历史类目调整未保留映射 |
| 经营目标表 | 渠道预算、GMV 目标、活动目标 | 月度约 200 行 | Excel，每月 | 目标版本通过群聊发送，缺少统一版本号 |

随本需求提供的《数据源与字段清单.xlsx》是 2026-08-24 的初步盘点，字段定义来自业务人员，不代表数据库最终结构。样例 CSV 已脱敏，仅用于验证字段读取和分析流程。

## 5.1 重点指标及已知口径差异

| **指标** | **当前常见口径** | **已知分歧** |
| --- | --- | --- |
| GMV | 支付成功订单金额，通常不扣除退款 | 财务月报使用退款后净 GMV；运营日报使用支付 GMV |
| 退款率 | 退款订单数 / 支付订单数 | 部分团队按退款金额 / 支付金额计算 |
| 准时送达率 | 实际送达日期不晚于承诺日期 | 承诺日期是否扣除节假日、偏远地区尚未统一 |
| 30 天复购率 | 首购后 30 天内再次支付的客户数 / 首购客户数 | 增长团队要求观察 60 天；同一天多单是否算复购未定 |
| 高价值客户 | 近 90 天支付金额和频次综合判断 | 阈值每月调整，目前没有版本化规则 |

# 6. 功能要求细化

### 数据资产

上传后应显示来源类型、文件大小、字段画像、更新时间、项目使用情况和来源变化提示。数据资产只有明确绑定后才进入某个项目。

### 安全查询

查询只允许 SELECT 或等价只读语句，拒绝 DDL、DML 和多语句。结果需记录所用数据源、SQL、执行时间、行数和内容哈希。

### 数据探索

同一数据片段可切换表格、柱状图、折线图和散点图。保存图表时应记录维度、指标和来源数据片段。

### 数据处理

质量画像需要给出缺失、重复、异常范围和建议；标准清洗与特征工程必须生成新产物，不覆盖原始数据。

### 模型实验

至少支持分类、回归和聚类。训练时显式选择目标列与特征，记录随机种子、数据划分、参数、指标、模型和预测。

### 项目对话

自然语言入口应能引用本项目已选数据和已登记产物。执行前应说明计划，执行后给出证据而不是只返回结论。

### 报告版本

报告正文以 Markdown 为内容底稿，图表只能引用已保存产物。修改和恢复历史版本均形成新版本并保留操作说明。

### Skills

业务方法应以可读说明和受控脚本形式扩展。脚本型 Skill 需要在无网络沙箱中运行，禁止直接访问宿主机敏感目录。

# 7. 技术、安全与运行要求

| **类别** | **初步要求** | **备注/待确认** |
| --- | --- | --- |
| 部署 | 原始经营数据优先保存在公司电脑或局域网环境 | 首期单机试点与 20 人访问目标存在冲突 |
| 模型与隐私 | 手机号、地址、姓名和会员标识不得发送到外部模型 | 需确认脱敏策略、模型部署方式和允许发送的字段 |
| 数据库安全 | MySQL 使用只读账号；禁止写回生产库 | 账号由 IT 配置，不写入项目源码或交付文件 |
| 性能 | 100 万行常见聚合查询 P95 小于 10 秒 | 测试设备暂定 16 GB 内存 MacBook；最大明细表超过 500 万行 |
| 可用性 | 无在线模型时，数据接入、查询、建模和报告仍可使用 | 自然语言对话可以降级，但不能影响确定性能力 |
| 备份恢复 | 项目、数据源配置、报告和模型产物可导出并恢复 | 备份周期、保存位置和保留时长未确定 |
| 浏览器 | Chrome、Edge 当前稳定版；Windows 用户可使用 WSL2 | 是否要求 Windows 原生运行待 IT 确认 |
| 审计 | 关键查询和模型实验需能回看来源与时间 | 目前不要求企业级操作审计和审批流 |

# 10. 启动前需要确认的问题

1. 首期到底是 3 名分析师单机试点，还是需要 20 人同时通过局域网访问？
2. GMV、退款率、准时送达率和复购率分别采用哪一套口径，谁有最终确认权？
3. 自然语言分析允许使用云模型、公司私有模型，还是只能使用脱敏后的字段和样本？
4. 一期必须直连 MySQL，还是先用每日脱敏文件完成流程验证？
5. 复购预测的业务动作是什么：筛选名单、解释特征，还是要求系统直接触达客户？
6. 模型验收使用准确率、AUC、召回率、F1 还是业务收益；训练和测试时间窗口如何切分？
7. 节假日、偏远地区和预约配送如何进入准时送达率计算？
8. 报告需要导出 HTML、PDF、Word 还是只在系统内查看？
9. 项目数据与产物保存多久，备份位置由谁维护，离线迁移是否必须？
10. 是否需要 Windows 原生运行，还是接受 WSL2 或公司统一 Linux 环境？
11. 国庆前“可用版本”指演示、试运行还是正式上线？
12. 验收问题集、对账 SQL 和业务基线数据由谁在何时提供？
