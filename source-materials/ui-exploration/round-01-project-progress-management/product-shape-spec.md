# 项目进度 UI 探索：产品形态 Spec

状态：`CONFIRMED_DIRECT_IMPLEMENTATION`

轮次：`round-01-project-progress-management`

目标项目：`FDEDeliveryWorkbench`

## 本轮边界

本轮只重新设计“项目进度”的前端信息架构、视觉层级与交互展开方式，不修改项目阶段、文档索引、任务证据、文件预览下载、阶段确认或 Session 路由等功能逻辑。

所有进度、日期、任务、阻塞和产物状态都必须来自现有真实数据；没有日期时继续显示“待确认”，没有任务证据时不生成百分比，文件存在也不等于阶段完成。

## 已核对的产品事实

- “项目进度”是跨项目的只读交付管理页面；“项目交付”是进入具体项目 Session 继续对话、修改和执行工作的工作区。
- 项目采用固定六阶段：需求调研、方案设计、项目开发、验证评估、客户试点、验收移交。
- 当前已有的数据能力包括：项目与 Session 摘要、当前阶段、真实或待确认的交付周期、阶段资料与阶段产物、研发核心文档、Feature、任务证据、里程碑、阻塞和研发收口产物。
- 当前真实样本项目能够读到 3/3 研发核心文档、7 个 Feature、47/47 项任务证据和 3/3 研发收口产物；Feature 日期尚未提供，因此只能显示“待确认”。该样本用于检验信息密度，不代表所有项目都有相同完整度。
- 已有 Markdown 产物可以只读打开并下载；阶段推进仍由 FDE 显式确认，不能由界面根据文件数量自动判断。

## 现状诊断及素材角色

### 当前产品事实

用户需求、项目级 PRD/Product Spec、F011/F020 Feature 规格、当前源码和真实样本数据共同定义本轮允许展示的对象与状态。

### 当前界面仅作为反例证据

当前界面只用来确认以下问题，不作为后续候选图的视觉参考：

- 多项目总览主要是统计卡片、项目卡片和独立时间线，无法迅速比较“各项目处在哪一阶段、当前在做什么、哪里需要关注”。
- 单项目页只有一条没有完整阶段名称和阶段工作摘要的六段进度条，用户难以建立全局方位。
- “阶段输入、阶段产出”被平铺成同一级页签，阶段主线与证据内容脱节。
- 需求、方案和研发阶段复用近似页面结构，主要替换产物列表，视觉上无法感知不同阶段的工作性质。
- Feature、任务、周期、里程碑、阻塞和产物虽然已经存在，但以纵向文档卡片为主，缺少研发模块与交付节奏的整体关系。

### 本轮不使用的参考

- 不使用其他项目界面冒充当前产品事实。
- 不把竞品截图、旧设计或当前截图作为首轮生成参考图。
- 首轮候选只依据本 Spec 与后续确认的页面功能 Spec，以纯文本描述生成。

## 目标用户与核心任务

目标用户是同时推进一个或多个企业 AI 项目的 FDE 开发者。

他进入“项目进度”时，需要连续回答五个问题：

1. 我现在一共有多少个项目在推进？
2. 每个项目处于六阶段中的哪里，真实周期是否明确，哪里有明确阻塞或待确认信息？
3. 进入一个项目后，它从需求到验收的完整交付路径是什么，当前阶段为什么停在这里？
4. 当前阶段正在推进哪些工作包，尤其是研发阶段有哪些 Feature、任务证据、里程碑和收口要求？
5. 我需要查看哪份产物、下载什么证据，或者回到哪个项目 Session 继续工作？

## 一句话产品形态

一个面向 FDE 开发者的只读交付管理工作台：以“项目组合 + 六阶段交付路径”为主轴，把当前方位、阶段工作、研发节奏和产物证据由宏观到细节逐层展开，而不是把它们摊平成文档列表。

## 核心体验承诺

用户进入页面后三秒内，应能明确看到：有哪些项目、各自在第几阶段、当前重点是什么、哪些信息真实缺失或受阻；进入单项目后，无论展开哪一类细节，完整六阶段方位和当前阶段都不会丢失。

## 主要用户旅程

1. 从左侧现有项目/Session 区进入“项目进度”。
2. 在项目组合视图中比较多个项目的阶段位置、真实周期、当前工作摘要和显式风险/待确认状态。
3. 选择一个项目，进入该项目的六阶段交付地图；保留返回全部项目的明确路径。
4. 选择某一阶段，先看到该阶段的目标、状态、输入、产出与确认条件，再按需展开专属工作内容。
5. 在项目开发阶段继续下钻到 Feature、任务证据、真实排期/待确认、里程碑、阻塞和收口产物。
6. 选择产物后在不丢失当前项目和阶段方位的情况下只读预览或下载。
7. 需要继续执行工作时，通过“进入项目交付”回到现有 Session；需要管理进度时留在本页。

## 交互模型

采用“总览定位 → 项目定位 → 阶段定位 → 工作包展开 → 证据查看”的渐进披露模型。

- 项目组合层负责比较，不把所有文档铺开。
- 单项目层始终保留完整六阶段地图；过去、当前、未来阶段必须有清楚且不夸大的视觉状态。
- 阶段层首先表达该阶段在交付链上的作用和当前状态，再展示阶段专属内容，不能只是换一批同样式的文件卡片。
- 研发层以 Feature/模块及其真实任务、周期、里程碑和阻塞为主要可视对象，文档是证据，不是页面的唯一组织方式。
- 产物预览是下钻层，打开和关闭后都应保持原来的项目、阶段和滚动上下文。

## 信息层级

### 一级：项目组合态势

- 项目数量和项目身份
- 每个项目的六阶段位置
- 当前工作摘要
- 已提供的真实周期，或明确的“待确认”
- 数据中已经存在的阻塞、冲突或待确认信号

### 二级：单项目交付全景

- 六阶段完整路径与当前阶段
- 已完成、当前、未开始/未知状态
- 每一阶段的目标、输入、产出和确认关系
- 当前阶段的下一项明确动作

### 三级：阶段工作包

- 需求阶段：项目资料与需求调研基线产物
- 方案阶段：方案文档、已确认架构及进入研发所需证据
- 研发阶段：核心文档、Feature/模块、任务证据、真实日期/待确认、里程碑、阻塞与收口产物
- 后续阶段：只展示现有数据能够证明的评估、试点或移交信息；没有数据时保持空态，不虚构完成度

### 四级：产物证据

- 文件名称、类型、状态、路径、更新时间和大小（数据存在时）
- 只读预览
- 下载原件
- 缺失、读取失败、待 FDE 确认和已纳入阶段确认等真实状态

## 首轮候选图的建议聚焦

首轮建议先探索“单项目交付全景”这一张关键页面：用户已从全部项目中选择一个项目，页面需要同时呈现完整六阶段方位、当前阶段的工作重点、研发 Feature/节奏与产物证据入口。

原因是当前最严重的问题发生在进入项目之后：用户失去全局方位，不同阶段又看起来像同一张文档页。项目组合总览将在该形态确认后作为同一产品的配套页面继续设计，而不是和单项目页混成一张信息过载的首轮候选图。

## 明确不是这些产品

- 不是通用 Dashboard、数据大屏或 KPI 驾驶舱。
- 不是 Jira、甘特图编辑器或新的任务管理系统。
- 不是文档目录、文件管理器或 VS Code 替代品。
- 不是 CRM、客户资源管理或成本管理系统。
- 不提供拖拽排期、任务编辑、自动计划、自动阶段推进或 AI 猜测完成度。
- 不改变左侧项目/历史 Session、项目交付入口、阶段门禁和文件读写边界。

## 需要确认的产品决定

1. 是否确认上述一句话产品形态和五层渐进路径？
2. 是否同意首轮先对“单项目交付全景”抽取 6 个差异明显的 UI 方向，再单独设计“多项目组合总览”？
3. 单项目全景中，是否同意“六阶段路径始终可见”，而产物预览作为下钻层出现，不再长期占据主视图？

确认后，本轮状态将进入页面功能合同阶段；在页面功能 Spec 再次确认前，不生成候选图，也不修改产品代码。
