# 门店维修验证版：快速检查

入口：http://127.0.0.1:4177 。无需安装依赖、无需模型密钥。

## 第一条业务链路

1. 选择 `R-1002`：应先看到人工应急提示，而不是等待分析后才提醒。
2. 点击“分析这条报修”：会读取资料并保存一条新的分析运行，不执行外部调用。
3. 确认“收银设备 / 网络连接”都是候选；系统不直接使用历史最终故障域作为答案。
4. 查看相似报修 `R-1003`。样本没有首报时间时会明确缺失，不声称已满足两小时重复判定。
5. 打开“关联与证据”，点击任意实体，检查关系、SourceId 和原件预览。
6. 点击“核对并存草稿”：填写真实操作人、确认边界，再保存。
7. 保存后页面应显示“已从本地服务读回”；刷新并进入“本地草稿”，记录仍在。
8. 导出的 JSON 包含 `externalWrite=false`、输入、来源、分析编号与原始图谱版本。

## 另外几个场景

- `R-1005`：焦味、插座发热触发应急优先；不让系统处理替代现场应急。
- `R-1010`：缺少设备与影响，优先级保持待定；提出不超过三个关键问题。
- `R-1008`：忽略政策等文本只作为报修内容，不改变权限或伪造派单结果。
- `R-1004`：设备身份不明、候选合同有限，不承诺维修费用。
- “新建报修”：可以录入已登记门店的内容，生成独立本地记录，再完成分析和草稿链路。

## 自动检查

`node --test backend/tests/*.test.mjs` 包含样本答案隔离、规则与时间窗、图谱来源、人工确认和版本校验、真实 HTTP 持久化、并发幂等、跨站请求拒绝、服务重启读回以及原件哈希对比。测试使用系统临时目录并自动清理，不向正常运行区填入假草稿。

## 与第五阶段工作台的关系

开发已在本目录完成；FDE 工作台本身没有修改。2026-09-07 按用户请求，已在原有 3080 项目登记现有 4177 服务和候选系统架构，新增第五阶段版本、指标与固定记录。刷新项目工作台即可查看；服务正在运行时应复用预览入口，不能再启动一份。服务终端目前由 Codex 持有，不伪称 DSH 内置终端已接管。

后续代码变化需要更新工作台架构和验证指标时，可在该项目 Agent 对话中提出：

本应用只读原有 `.fde/` 和阶段产物，不直接调用工作台内部 API 或替代 FDE 决定。

## 本轮能力边界

- 12 条脱敏报修样本、35 份原始资料，图谱为已有 56 实体/56 关系快照。没有重新运行 Semantica，也没有付费模型。
