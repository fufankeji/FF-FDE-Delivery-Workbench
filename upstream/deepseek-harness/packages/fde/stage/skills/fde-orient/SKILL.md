# 项目启动与方向确认

先弄清“实际被要求完成什么”，再安排工作。一次有效定向应留下可复用的事实与未知，后续工作直接读取，不每轮重新问一遍。

## 1. 先判断是否已有有效定向

读取当前项目已授权的主报告、事实确认清单和流程基线。已有记录且边界仍成立时，按继续工作处理；发生实质变化时保留旧说法和生效时间，提出重新定向。不要删除原记录，也不在当前仓库之外创建另一个工作区。

平台目录与写入字段遵循 [阶段记录规则](../qualify-ai-workflow/references/stage-records.md)。纯阅读或讨论不强制创建任何文件。

## 2. 先从材料推导，再询问缺口

读取用户提供的诉求、项目说明、已有方案及当前阶段记录。任务涉及现有系统且授权允许时，再查看 README、目录、版本和近期变更；没有代码授权就不访问代码。已有材料能回答的问题不再次追问。

确认当前是否有系统、实际维护状态、业务范围、已经试过的办法和访问条件。明确哪些是材料事实，哪些是推断；不要仅凭仓库大小或技术栈判断工作难度。

## 3. 补齐会改变方向的问题

按影响选择本轮确有缺口的问题，不机械问全套：

- 客户原话到底要求做什么，原始材料在哪里？
- 谁提出要求，谁真正支持项目，谁负责结果和批准？
- 时限来自合同、监管、业务高峰还是期望日期？
- 怎样算完成，由谁验证；若没人能回答，这就是关键缺口。
- 当前明确允许访问哪些材料、系统和环境？
- 之前谁试过什么，结果怎样，为什么停止？

用户不知道也是发现，登记待确认事项及核对人；不要要求其编造答案。记录表面诉求与可能的真实问题，问“什么都不做会发生什么”来核对必要性，但不要在定向时展开完整需求或技术设计。

## 4. 识别任务类型与主要约束

已有系统增强、组织内新建、系统集成、迁移升级、救火稳定、纯评估、数据分析、软件配置、退役、监管整改和探索验证的主要约束不同。使用 [任务类型与能力选择](references/engagement-types.md) 判断当前类型及下一步，不把未安装的能力当作可调用工具，也不直接执行其他产品的插件安装命令。

没有合适类型就说明是组合任务，并写清依据；不要强行套类别。监管时间可能固定，应尽早讨论范围；商用软件任务先查配置和供应商升级边界，不默认写代码。正在发生事故时先解决事故，本 Skill 只在安全后补定向。

## 5. 确认工作边界和责任

范围由明确授权的业务问题、项目、材料和环境决定，不由可访问目录决定。分别记录：目标、明确不做的事项、当前成功说法、时限原因、约束、已有访问、已尝试方案、关键角色和未知。

现有项目文件和用户数据继续原地维护，文件追踪与外部发布遵循项目规则；本 Skill 不擅自改变 Git、部署、权限或数据保留设置。

## 6. 排出最短的下一步

通常只列下一轮真正需要的三到五项动作；简单任务更少，不为了填满列表加载全部 Skill。每项写清“为什么现在做、由谁做、需要什么输入、看到什么结果就结束”。访问审批有等待时间时，应尽早提出明确访问请求，但申请不等于已经获批。

本平台第一阶段默认回到 `qualify-ai-workflow`；需要知情者取证用 `knowledge-interview`，找责任人用 `ownership-map`，明确需要代码事实才用 `repo-recon`，有待负责人决定的结论才用 `stakeholder-brief`。实质边界冲突使用 `reframe-ai-engagement`。其他阶段能力只有实际可用且当前任务获授权时才进入后续建议。

## 输出与停止

向主报告贡献“原始要求、真实问题候选、任务类型、约束和下一步”，向确认清单贡献缺口与核对人。可参考 [项目定向记录](assets/orientation.md)，但不另建平行最终稿或额外必备产物。

当真实任务、责任关系、约束和下一步足以继续工作时停止。原作者不等于维护者，提出要求的人不等于项目支持者，访问能力不等于操作授权。候选定向不能代替 FDE 的阶段确认。
