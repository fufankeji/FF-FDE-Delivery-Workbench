# 责任与决策权映射

回答三个不同问题：谁知道、谁负责、谁能说“可以”。组织图和提交数量只能提供线索，不能直接证明决策权。

## 1. 先界定映射范围

读取当前项目定向、候选工作流和已有系统记录，只映射本次业务问题所涉及的组件或职责。单人仓库、责任已经明确的区域直接复用现有记录，不把责任地图变成每次提问的前置手续。

## 2. 读取声明的职责

在授权范围内检查责任表、服务目录、CODEOWNERS、OWNERS、团队文档和相关流程；有代码时可用 `rg --files --hidden -g CODEOWNERS -g OWNERS -g '!**/.git/**'` 找到真实文件。检查嵌套模块定义，不能只读仓库根部一份。

声明是候选而非事实终点：团队调整、人员离开和系统迁移都可能让它失效。业务决策权必须来自实际授权或负责人确认，不从代码所有权推出。

## 3. 用近期活动识别实际维护

仅当需要系统责任证据且已获代码授权时，按真实模块路径查看近期提交、原始作者和评审记录。可使用 `git log --format='%an' --since='12 months ago' -- 实际路径` 与 `git log --format='%an' --reverse -- 实际路径`；时间窗口随项目活跃度调整，不把示例窗口当硬规定。存在评审记录或 Reviewed-by/Approved-by 时再核对谁实际参与。

区分原作者、当前维护者和偶发贡献者。近期相关活动通常比累计数量更有价值；长期不活跃的原作者可能提供历史知识，但不自动具备当前审批权。机器人、合并提交和批量格式化会扭曲数量，不做人员绩效排名。

## 4. 找出责任交界和无人负责区域

按任务涉及的组件比较维护者与上下游关系，找出责任变化的位置，而非给整个仓库贴一个团队标签。记录长期无活动、仍被依赖却无人认领或多个团队互相指向的区域。

无人维护不等于系统已停用。把仍在运行与缺少责任人的证据分别登记，并说明会怎样影响访谈、评审、验证和交付周期；尽早请求 FDE 协调，不替组织指定负责人。

## 5. 核对决策权与协作方式

对当前范围明确：谁必须评审；谁能批准变更或例外；谁要被征询、谁只需被告知；谁的异议会阻止当前决定，以及其权力依据。技术专家不等于批准人，合并权限也不等于生产变更授权。

只记录工作所需的联系渠道、时区和沟通习惯，例如是否先开工单、是否希望评审前先沟通。不要采集私人联系信息或擅自发送消息。

## 输出与停止

使用 [责任记录模板](assets/ownership.md) 为每个在范围内的区域记录声明责任人、实际维护者、最后活动、责任确认、决策权、联系办法、证据与未知。尚未核实的结论将 state 设为 unverified；逐条引用 project-file、system 或 interview 证据，格式见 [阶段记录规则](../qualify-ai-workflow/references/stage-records.md)。

当每个相关区域都有已核实责任人，或已明确标记责任缺口及核对动作，并知道当前任务需要谁评审和决定时停止。结果回写主报告与确认清单，由 `qualify-ai-workflow` 维护候选记录；不得因生成地图而批准项目或推进阶段。
