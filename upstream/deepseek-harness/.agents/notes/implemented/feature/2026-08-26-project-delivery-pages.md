# Agent Note: Project delivery pages over Workspace and Session facts

Status: implemented

English | [中文](2026-08-26-project-delivery-pages.zh.md)

## Problem

The FDE workbench uses one Harness Workspace as one delivery project and lets that project contain several ordinary Sessions. Conversation and the right development dock are suitable for doing the work, but neither is a truthful place to compare every project, its delivery stage, schedule, and activity. API documentation, system architecture, usage analysis, and evaluation optimization are also project artifacts or project-wide evidence: tying them to one Session would split facts that every Session in the Workspace must share.

The useful community plugins have narrower ownership. `dsh-openapi` loads one static process-wide API directory, `dsh-planchart` stores one Session plan and adds a steps overlay, `dsh-observe` exports runtime records to configured backends, and `dsh-eval-harness` owns Agent-driven regression tools. Installing each UI unchanged would either cross project boundaries, duplicate the development dock, or require external infrastructure before the local workbench can explain its own project.

## Decision

`@deepseek-ai/dsh-client-ui-fde-project` registers “项目进度” in `sidebar.footer.action` and renders the page through `shell.overlay`, offset by the live sidebar width. The page reads the Workspace and Session object layers, browser-local creation metadata, and the Workspace-keyed stage route. It shows stage segments and confirmed dates rather than inventing a percentage. Entering a project selects the latest visible ordinary Session in that Workspace, creates or reuses the first blank Session only when none is recoverable, opens it, and closes the global page. Entering a project detail forces a fresh project-artifact snapshot so Agent-written files and architecture confirmations do not remain hidden behind the controller's first-load cache. The current stage can be returned exactly one step after the FDE opens a warning panel, provides a reason, and confirms again. The page preserves every artifact, shows the latest audit, marks the affected range “待重新确认”, and calls the terminal action “重新打开项目”.

The system initially opens a product home before any sidebar operation is selected. It explains the outcome-first delivery method and provides an explicit action into the unchanged Project Progress page. A labeled animated example follows a vague brief through field evidence, minimum safe mechanism choice, and customer acceptance; the adjacent principles and canonical nine-step method explain why work advances. The nine steps remain a presentation and learning layer mapped onto the six durable project stages. They neither add another lifecycle state nor infer project completion, and reduced-motion preferences stop their ambient and sequencing animations.

The same client package registers four project views in `conversation.view`: API 文档, 系统架构, 用量分析, and 评估优化. Each view derives Workspace ownership from the current Session's membership. `@deepseek-ai/dsh-fde-project` exposes one trusted snapshot route that resolves an explicit registered WorkspaceId before reading `.fde/api-docs.json`, `.fde/architecture.json`, or `.fde/evaluations/`; a caller-supplied directory never selects the project.

The OpenAPI tools reuse the parser, catalog, validation, redirect, private-network, credential-header, timeout, and bounded-response implementations from MIT-licensed `dsh-openapi` commit `fb854355b89e495ded090b9e2eb94c33430d2366`. The upstream plugin's static catalog is not mounted directly. `openapi_list`, `openapi_describe`, and `openapi_call` instead resolve the calling Agent's cwd through `workspaceRegistry` on every execution and load only that Workspace's explicit configuration. Tool schemas stay constant across projects, while the execution path enforces project isolation and defaults to `GET` and `HEAD`.

The system architecture uses the grouped-node-and-edge idea from MIT-licensed `dsh-planchart` commit `e63a6359ed43e6ae35cac505f10a8d128f53eba7`, without its Session plan or right-side steps UI. `architecture_get` returns the exact project revision; `architecture_set` accepts one complete candidate only when its `expectedRevision` matches, validates bounded groups, nodes, and edges, then commits by locked atomic replacement. The solution-design Skill and the browser refresh action require the Agent to inspect confirmed documents and real source entry points, services, stores, integrations, deployment configuration, and outputs before modeling. Candidates preserve stable ids, order two to seven responsibility groups along the primary path, distinguish current implementation from planned components, and retain only major nodes and material runtime, data, control, or dependency relationships. During development, only an explicit request or a structural change to a major service, entry, store, integration, deployment boundary, or data path triggers the same complete-candidate update; internal refactors do not.

The browser derives a responsive signal-flow layout from those ordered groups, nodes, and edges, with animated connections, node focus, related-path emphasis, light/dark theme adaptation, zoom, SVG/PNG export, and an exact-revision confirmation route. A candidate row on Project Progress is navigation, not confirmation: it opens the target project's latest visible ordinary Session and selects the System Architecture view through the scope-addressed Conversation service. The confirmation action remains inside that full view; a confirmed row becomes inert on the next fresh snapshot. Generating or modifying a candidate is an explicit prompt to the current Agent, and confirmation does not advance the delivery stage.

`dsh-observe@0.2.0` from commit `64791ff93ac01bac5bb6e6a14f48d072b479464b` is installed with `enabled: false`, no OTLP or Langfuse backend, and prompt/completion capture disabled. The local 用量分析 page therefore aggregates existing Session `sessionStats` and `tokenUsage` projections without capture or outbound traffic. A later deployment can configure an external backend without replacing the project page.

`dsh-eval-harness` commit `2f59376e2a2f22c151f75de446d5cde764dd5aff` supplies `eval_run`, `eval_gate`, and judge-calibration tools. Its obsolete exact DSH dependency numbers are redirected to this locked Harness checkout; its source is built during the approved Git dependency preparation step. A Host pre-execution guard confines cases, runtime output, and gate reports to the calling Agent's Workspace, rejects symlink traversal and model-selected executables or profiles, and denies Judge calibration in V1. The 评估优化 page only queues an `eval_run` instruction after a user click, reads reports from the current project's bounded directory, and lets the user atomically approve one indexed report as the baseline. Page loading and automated checks never start a model evaluation.

Validation decisions remain separate from measured results. Project Progress lets the FDE add a reasoned acceptance to one unmet required metric only through an exact-contract same-origin action. The Host rechecks the current plan digest and metric eligibility under the validation-contract file lock, writes `result.manualAcceptance.reason` and `acceptedAt`, and preserves NOT_RUN/FAIL, evidence gaps, values, and notes. A complete acceptance removes only that metric's blocker; stale digests, optional metrics, normally satisfied metrics, repeated decisions, and empty reasons are rejected.

Project Progress also owns the deployment-trial and acceptance-handover detail pages. The Host projects bounded schema-v1 project files, project-local evidence, fixed outputs, blockers, and the terminal completion state. The deployment page binds an FDE issue-acceptance action to the exact displayed contract digest; the action requires a reason and changes only that issue. Target-environment authorization and the trial-ready conclusion remain a separate exact-contract FDE action that becomes available only after evidence, issue decisions, and fixed outputs are otherwise complete; it atomically writes the two decision fields without executing deployment, stop, or rollback. The handover page accepts a bounded array of enterprise-acceptance evidence and adds one exact-digest, file-locked four-step FDE form for acceptance status, deliverable availability, condition decisions, and evidenced training/access/operations transfer. The Host preserves deliverable identity and rejects stale digests or changed item sets. This action records facts only and remains separate from the final two-step stage confirmation, while `completed` keeps the final handover evidence visible.

## Alternatives considered

**Put the project overview in a Conversation tab.** A Session tab disappears into whichever project is already open and cannot provide a natural multi-project entry. It also mixes project management with the page used for implementation work.

**Confirm architecture directly from Project Progress.** A compact artifact row cannot show the complete architecture, dependencies, or revision context. Project Progress therefore guides the FDE to the full System Architecture view and never owns the confirmation mutation.

**Install every community plugin unchanged.** The static OpenAPI catalog can expose one project's APIs to another Agent, and the planchart steps overlay duplicates project stages while remaining Session-owned. Their reusable mechanisms are retained behind Workspace ownership instead.

**Require Langfuse before showing observability.** That makes local delivery diagnostics depend on Docker, credentials, outbound access, and a second application. Existing durable Session projections provide an immediate project summary, while the exporter remains an explicit optional layer.

**Build a general project-management and evaluation platform.** Customer management, asset reuse, arbitrary Gantt editing, scheduled evaluations, and a full APM product exceed the single delivery-chain release. The implemented pages expose current project facts and explicit actions without creating those adjacent products.

## Consequences

The left sidebar remains the stable way to move between project management and delivery work, the center remains the official Conversation, and the right dock remains Files, Editor, and Git. The product home gives a first-time user the conceptual route, while returning operators enter the same portfolio through either its explicit call to action or the existing sidebar entry. API, architecture, usage-analysis, and evaluation-optimization state survives across Sessions because project files and Host records, not component memory, hold the facts. Cross-plugin deep links use a scope-addressed Conversation view action rather than DOM clicks or direct persistence edits. Missing files, disabled exporters, invalid reports, and unavailable API pages stay explicit rather than becoming demo data.

Five project tools add stable schemas to Agent requests: three OpenAPI tools and two architecture tools. Their results enter context only after invocation. Architecture quality depends on evidence available to the Agent, so missing source or unresolved document differences remain labeled candidate facts rather than fabricated certainty. Stable ids keep focus and change review coherent across revisions, while limiting groups and relationships trades exhaustive call graphs for a legible project-level system model. External observability exports remain absent until deployment configuration opts in, and evaluation remains potentially billable only after a direct click. Company and schedule metadata still belong to the current browser's Workspace view store, iframe refusal has an external-open fallback rather than a cross-origin bypass, and the evaluation page delegates long-running process control to the current Agent and its existing cancel path.
