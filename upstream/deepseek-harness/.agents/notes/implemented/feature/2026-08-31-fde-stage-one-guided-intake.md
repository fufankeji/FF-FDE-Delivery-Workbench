# Agent Note: Stage one begins from a problem or project material

Status: implemented

English | [中文](2026-08-31-fde-stage-one-guided-intake.zh.md)

## Problem

The first FDE stage previously looked like a generic Agent composer with a technical prompt already filled in. It did not explain whether an operator should describe an uncertain customer problem, upload customer material, or do both. It also made durable project upload look like a prerequisite for starting the Agent, even though a real engagement can begin from an incomplete spoken request. Users could not see how the built-in discovery capability would turn either kind of input into progressively clearer facts and stage artifacts.

## Decision

The native Harness composer is the single Agent entry across every FDE stage. Stage one is a business workbench around that executor instead of another textarea or send action. The left project rail owns lifecycle orientation, so the main surface does not repeat the stage number, project name, or full eight-stage path. Its plain-language objective is to first understand how the customer works today and where the problem occurs, then decide what to solve first. One continuous progress rail shows four business actions: hear how the customer describes the work, reconstruct the actual process, confirm whether the problem is worth solving, and decide the next step. Only the current and immediately following actions receive status copy, so the rail explains progress without repeating technical prerequisites.

A collapsed “Methods for this stage” tree sits directly under the current stage in the left rail. It explains which methods the platform applies without mixing technical names into the primary task. The tree projects only the seven stage-one methods actually registered by the product and gives them business labels: confirm the project direction, interview business operators to reconstruct actual work, identify owners and decision makers, inventory existing systems and material, decide whether the problem merits further investment, reconcile conflicts and adjust scope, and prepare a decision brief for responsible leaders. Selecting a method opens a read-only right drawer that renders its full definition, usage guidance, and original source as Markdown; technical identifiers remain collapsed. The tree never scans the operator's machine, global Skills, or other projects, and exposes no run, install, enable, or edit action. It is an explainable method catalog, not a second Agent entry. The first three delivery-environment tabs are fixed as Project workbench, Agent chat, and Run trace, with Project workbench always first; stage-specific views can only follow them.

The Host still projects the existing fixed requirement files as stable Artifacts, but the interface does not expose those internal document names. It presents them as a customer-current-state record, items to confirm, a business-process explanation, and a conditional project-adjustment record. It also reads the project-scoped `.fde/discovery/workflows.json` catalog so identified real business processes become visible as “business processes to confirm” instead of remaining buried in chat or appearing as internal system workflows. With no result, the area keeps only one compact guidance row; persisted results use a compact single-column list. That projection derives the current work, candidate-artifact readiness, and honest blockers. File presence means only that a candidate carrier exists; it does not confirm the underlying fact or complete the stage. The operator can preview existing artifacts, while Go, Revise, Narrow, and Stop remain explicit FDE decisions.

Once the candidate material is ready, “Submit for FDE review” opens a stage-one review mode inside the current project instead of routing to the multi-project center. The review combines the current candidate business process, original customer material, evidence states, stage records, and unresolved facts without changing the project stage. Only “Continue to the next stage” followed by a second explicit confirmation calls the durable stage service with the current revision; success presents stage two directly. Continuing investigation, narrowing the problem, and pausing the problem all remain in stage one and prepare an editable task in the native Agent conversation.

The operator speaks directly in the existing composer. A business action selects Agent chat, collapses the left lifecycle rail, opens the current project's file tree on the right, and prefills one editable business question; the operator must complete or confirm it before sending. Existing draft text is preserved instead of being replaced or sent automatically. After the operator sends, the current stage prompt loads the bundled stage Skill behind the scenes; Skill names, evidence fields, context limits, and stage-control rules never enter the user message. When the operator explicitly chooses to start from archived customer material, the prefilled question names the current project's archived paths; ordinary conversation does not silently add them. Entering the project workbench itself keeps the technical workspace closed; file preview and other applicable technical operations can also open the file tree, code, diff, terminal, or browser within the current project.

Project material is an optional helper inside the native composer, not a second workflow choice. The compact "Have customer material? Upload" action reuses the project-scoped upload control and resolves the exact Workspace from the active Session. It continues to archive files in the visible `fde-resources/` directory without creating a message, triggering an Agent turn, or claiming that the file is already model-visible. The left project rail therefore exposes neither a duplicate Agent action nor a duplicate upload action.

On desktop, the stage objective, current work, and candidate workflows occupy the left execution column instead of extending across the artifact area. Stage artifacts begin collapsed as a full-height narrow rail whose only visible control is an artifact icon with its required-output count; hover or keyboard focus exposes one unwrapped tooltip with the label and count. Expanding it opens the separate review rail. The workbench stays inside the available viewport: business content and an expanded artifact rail scroll inside their own columns while the native composer remains available at the bottom. This local presentation state does not change Artifact, evidence, or stage state.

The current-work card explains the single main task as starting from one recent real case and exposes only the “start mapping the real process” primary action. “Start from customer material” appears only when project material exists; “continue checking inconsistent accounts” appears only after the platform has produced a project-adjustment record. These business actions reflect the current evidence gap and do not imply that stage one runs only two Skills. The artifact counter explicitly reports the three required records so a conditional record cannot make the completion denominator ambiguous. In a desktop stage view, the execution column calculates its usable height from the live composer height published by ConversationRoot instead of merely appending blank scroll space or guessing fixed pixels. The composer stays aligned with the execution column and widens when the artifact rail is collapsed.

## Alternatives considered

**Keep the generic composer as the entire stage page.** Rejected because an unexplained blank composer hides the current business task, the clarification process, and the expected outputs.

**Add a dedicated stage textarea and start button above the native composer.** Rejected because two Agent inputs compete for attention and make the operator guess which one actually runs Skills and tools.

**Automatically attach every uploaded project file to Agent context.** Rejected because durable project storage and model-visible context are different user intentions. Automatic attachment would introduce context pollution and unclear authorization.

## Consequences

An operator sees the exact stage purpose, four guided steps, emerging candidate workflows, candidate outputs with their missing evidence, and the next manual decision around the executor. The left rail owns lifecycle position, the workbench owns stage meaning, the conversation owns execution, and the technical workspace owns files and code only when requested. Stored customer material remains durable and reusable across Sessions, but upload is optional and does not imply model access. The Workspace-resolved upload action and business projection add small, explicit contracts covered by Host and component tests.
